# 写作与取证约定

这一页写给两类人：想接着写本站内容的队友，以及想判断「这条结论能不能信」的读者。

## 三档可信度

文章里的判断只允许落在三档里，并且必须能被读者分辨：

| 档位 | 长什么样 | 要求 |
|---|---|---|
| **实测** | 「实测：1 909 867 字节回写后逐字节相同」「在 kards 语料 34 个资产 / 945 个函数上跑过」 | 必须带条件：哪个版本、什么输入、怎么跑。最好给命令 |
| **推断** | 「推测 UE 走 `StaticEnum` 注册链 + 间接访问」「更像是……而不是……」 | 必须显式写出「推测 / 更像 / 大概率」，并给出推断依据 |
| **未验证** | 「未在真机验证」「运行期行为未在游戏内验证」 | 必须显式标注，不能靠读者自己猜 |

反过来也成立：**不要把未验证的东西写成实测**。这类错误一次就够毁掉整站的信用。

## 写「边界」的方法

每个项目页的边界一节，按这个顺序写：

1. **支持的版本**（「只验证过 UE 5.6 / 只验证过 v21」）——不是「最新版」，是具体版本号。
2. **不做的事**（删除既有条目不在支持范围 / 不做新卡 / 不做可视化编辑器）。
3. **已知的破损点**（哪些输入会失败、失败时报什么）。
4. **需要自备的输入**（游戏 APK、mapping 文件、SDK dump、AES 密钥）。

边界写在前面，是因为读者通常带着一个具体需求来，他需要先确认能不能用，再决定要不要读实现。

## 数字要带条件

「快」「小」「一致」这种形容词一律换成数字 + 条件：

- ✅ 「7 GB 母 pak + 1 张贴图 → 685 KB 产物，3.2 s，峰值临时空间 1.6 MB」
- ❌ 「极快且几乎不占空间」

同理，凡涉及大小/数量/耗时，都写清是哪一次测量。

## 代码块与命令

- 命令尽量是**能直接粘进终端**的完整形式，带参数说明。
- 输出示例保持原样，包含报错信息——报错比正常输出更能说明工具的边界。
- 涉及路径的地方用占位符并说明（`<game>\kards\Binaries\Win64`、`<kards.usmap>`）。

## 引用与版权

- 引用别人的结论时给出处：[UE5 运行时逆向](/ue5-re/)与[蓝图逆向](/ue5-bp/)的每节末尾都有
  [出处清单](/ue5-re/appendix/sources)条目。
- 不转载、不打包游戏数据、美术、音频、密钥。示例一律用**合成数据**或自备输入。
- 站内的表格、指令表是自己实测整理的，不复制粘贴第三方文档。

## 语言风格

- 中文为主，术语保留英文原词（`ubergraph`、`EX_Let`、`cooked`），不硬翻。
- 一句话说一件事实。避免「众所周知」「非常简单」这类评价。
- 面向读者的第二人称尽量少用「您」，本站统一用「你」。
- 需要强调的地方用粗体，不用太多感叹号。

## 页面结构

项目页与专题页大致遵循同一套骨架（不强制）：

```text
一句话定义（这是什么、给谁用）
│
├─ 项/值 表（语言、运行时、仓库地址）
├─ 这是什么（使用场景）
├─ 架构（分层 / 模块 / 数据流图）
├─ 实现细节（决定成败的那几处）
├─ 快速开始（能跑起来的最短路径）
├─ 边界（不支持什么）
└─ 相关项目
```

专题页额外要求：每节末尾给出处；跨章节的结论在前面的章节里至少出现一次并用链接指回。

## 本站的更新方式

- 内容全部是 Markdown + frontmatter，没有客户端组件；`srcDir: docs`。
- 项目总览里的仓库表由 `npm run sync` 生成，手改会被下一次同步覆盖。
- 新的项目页需要在 `.vitepress/config.mjs` 的侧边栏里登记，否则只能在 URL 里直接访问。

更多实现细节见[本站是怎么搭的](/lab/colophon)。

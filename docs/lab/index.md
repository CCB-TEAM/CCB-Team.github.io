## 几条零散的经验

下面这些是写别的页面时反复用到、但塞不进任何一篇文章的判断，先摊在这里：

- **先分清「容器」和「语义」。** `.pak`、`AssetRegistry.bin`、`.uasset` 都是容器；
  「这是一个什么类、有几个属性、这个函数在算什么」是语义。两层的错误长得很不一样：
  容器层错了是「游戏起不来」，语义层错了是「游戏起来了但行为不对」。分层的另一个好处是
  容器层可以做到「不动就逐字节不变」，语义层做不到（[solstice-bin](/projects/solstice-bin) vs
  [UAssetRegistry](/projects/uassetregistry)）。
- **字节级一致是极强的验证手段，但它证明不了语义。** 反过来，语义正确也完全可能字节不同
  （比如 tag 值统一按 `AnsiString` 重写）。这两种「对」必须分开说。
- **所有「写回」工具都要能回答：写完之后，其余地方变了没有？** 我们惯用的硬闸是
  「目标函数之外的字节 SHA-256 不变」+「读回再反编译一遍」。
- **报错比静默好，静默比错位好，错位比崩溃好。** 崩溃至少能被发现；错位（偏移算错一个字节）
  会变成几周后一个没人能解释的诡异 bug。
- **验证环境要能重建。** 一份「我这儿是好的」的结论，如果不带版本号、build id 与命令，
  基本等于没有。
- **写文档时把「不支持」放在前面。** 理由很简单：读的人通常是被某个具体需求推过来的，
  他要先确认你能不能满足他，再决定要不要理解你的实现。
